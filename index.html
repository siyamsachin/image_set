00

One src means one file for every screen

A plain <img src> forces you to pick a single file for a 360 px phone at 3x and a 1440 px desktop at 1x. Whichever you pick, one of them is wrong. The three tools below each remove a different part of that compromise.

ToolThe question it answersWho decides
srcsetWhich copies of this same picture exist, and how wide is each one?You list, browser picks
sizesHow wide will this image actually be drawn on the page?You must tell it — it cannot measure before layout
<picture>Which different picture (crop or file format) should be used at all?You decide, by rule; first match wins
Read this first

srcset and sizes are a hint — the browser may pick any candidate it likes (it knows your data saver setting, network and cache). <picture> with media or type is a command — the first matching <source> always wins. Use the hint for resolution, the command for art direction and formats.

01 · SRCSET

"Which files exist, and how many real pixels does each one have?"

Every entry declares a file and its real width

The image below is meant to fill its container edge to edge. Below are three versions of it. Drag the width control — the first two are stuck with whatever single file was hardcoded, the third re-picks as the frame changes.

Frame width360px

What actually happens

  • The number before w is the file's real pixel width. It is not a breakpoint, not a viewport width, and not a promise about layout. Get it wrong and every later calculation is wrong.
  • The browser works out how many pixels the slot needs — slot width in CSS px × device pixel ratio — then picks the smallest candidate that covers it.
  • No sizes here, so the browser assumes sizes="100vw". In this demo that assumption is correct, because the image really is full-bleed. Section 2 is what happens when it isn't.
  • src stays as the fallback for browsers that ignore srcset. Point it at a mid-size file.
  • width and height are the largest candidate's dimensions. They only supply the aspect ratio so the layout does not jump — CSS still controls the rendered size.
Why the first two panes are both wrong

The 320 px file is 9 KB and turns to mush the moment the slot is wider than 320 CSS px on a 1x screen — or 107 px on a 3x phone. The 2000 px file is 156 KB and looks perfect everywhere, but a 360 px phone is throwing away roughly 90% of the pixels it just paid to download. srcset is how you stop choosing between the two.

01b · SRCSET

"What if the image is always the same size?"

Fixed-size images use x, and need no sizes

When the rendered width never changes — an avatar, a logo, a fixed thumbnail — there is nothing for sizes to describe. Use x descriptors and let the browser pick on pixel density alone.

Frame width560px

The frame width does nothing here — that is the point. Only your screen's DPR decides.

  • x and w descriptors cannot be mixed in one srcset.
  • A candidate with no descriptor is treated as 1x.
  • sizes is ignored entirely when you use x. If you find yourself wanting it, you actually needed w.
02 · SIZES

"How wide will this image be drawn, before any CSS has run?"

Without sizes, the browser assumes full viewport width

Images are fetched by the preload scanner, before CSS is parsed and long before layout. The browser genuinely cannot know your image sits in a 38%-wide column, so it defaults to 100vw and over-fetches.

Both panes below have the identical srcset and the identical CSS: the image is full width below 700 px, and 38% of the frame above it. The only difference is the sizes attribute. Push the width past 700 and watch the two diverge.

Frame width1040px

How to read a sizes value

sizes is a list of media-condition / length pairs, first match wins
sizes="(min-width: 1200px) 380px,   ← big screens: a fixed 380px slot
       (min-width: 700px) 38vw,     ← tablets: 38% of the viewport
       100vw"                       ← everything else: full width (no condition, must be last)
  • The lengths describe layout, not files. 38vw means "this image occupies 38% of the viewport", nothing about which file to serve.
  • The browser then computes chosen length × DPR and matches that against your w descriptors. On a 2x screen a 400px slot asks for an 800 px file.
  • Media conditions here are viewport queries, not container queries — they cannot see the parent element.
  • Only valid with w descriptors. Harmless but ignored with x.
  • When sizes and CSS disagree, sizes wins for the download and CSS wins for the display — so you silently get the wrong file with no visual clue. This is the single most common bug in this area.
sizes="auto"

Newer browsers accept sizes="auto" on a lazy-loaded image (loading="lazy"), which lets them measure the laid-out element instead of trusting you. It does not work on eager images, because nothing is laid out yet when they are fetched. Keep a normal sizes list as the fallback: sizes="auto, (min-width: 700px) 38vw, 100vw".

03 · PICTURE

"Should this be a different picture, not just a smaller one?"

When the crop must change, not just the resolution

srcset only ever scales the same photo. If a wide hero makes the subject unreadable on a phone, no amount of resolution switching helps — you need a different crop. That is art direction, and it is what <picture> with media is for.

Drag below 640 px and watch the second pane swap to a tall, tightly-cropped file while the first pane just keeps shrinking the same letterbox.

Frame width360px

Note the byte count: on a phone the art-directed version is often the heavier download. That is the trade — you are paying for an image the user can actually read.

The rules that trip people up

  • <picture> renders nothing itself. It is a wrapper that feeds the <img> inside it. The <img> is still what you style, what you set alt on, and what appears in the DOM.
  • The <img> must be last, and it is mandatory. Without it nothing renders at all.
  • First match wins, and evaluation stops there — order your sources narrowest-condition first. This is unlike srcset, where the browser is free to choose.
  • Each <source> carries its own srcset and sizes. They do not inherit from the <img>.
  • Put alt, width, height, loading and fetchpriority on the <img> — never on <source>.
  • Different crops have different aspect ratios, so a single width/height pair cannot prevent layout shift for both. Give each <source> its own width/height, or pin the ratio in CSS per breakpoint.
Test before you reach for it

If the only thing changing is how many pixels you need, use srcset + sizes and let the browser optimise. Reach for <picture media> only when the content of the image must change. Art direction removes the browser's freedom to choose, so it costs you something.

03b · PICTURE

"Can this browser decode a smaller format?"

Same mechanism, driven by type instead of media

Identical pixels, three encodings. The browser walks the list and takes the first type it can actually decode, so modern formats go first and JPEG is the safety net at the bottom.

Frame width560px

The badge burned into each file tells you which format your browser chose. Same image, same perceptual quality, 44% fewer bytes on AVIF.

  • Order matters and it is strict: smallest/newest format first, universal fallback last.
  • No media needed — type alone is a valid condition.
  • You can combine both on one source: <source type="image/avif" media="(max-width: 640px)" srcset="…">.
  • This is the one <picture> use that is almost always worth it, because it never changes what the user sees — only what they download.

All three at once

A real hero: crop changes on phones, format changes by support, resolution changes by device — and sizes keeps the maths honest.

Above-the-fold heroes

A hero should be fetchpriority="high" and never loading="lazy" — lazy-loading your LCP element delays it past the point the browser would have fetched it anyway. Lazy-load everything below the fold instead.

How this maps onto next/image in this repo

Next.js generates srcset for you from deviceSizes and imageSizes, but it cannot guess sizes — that is still entirely on you, and getting it wrong costs exactly what section 2 showed.

The section-2 example, written for this codebase
<Image
  src="/story-assets/tractor.png"
  alt="TAFE tractor"
  width={2000} height={1334}
  sizes="(min-width: 700px) 38vw, 100vw"
  className="w-full h-auto"
/>

// Art direction — next/image has no media support. Two Images works, but see the warning below.
<Image className="block sm:hidden" src={heroTall} sizes="100vw" /* … */ />
<Image className="hidden sm:block" src={heroWide} sizes="100vw" /* … */ />
The catch with the two-Image trick

An <img> hidden with display: none is still downloaded — the fetch is triggered by the element being in the document, not by it being painted. So the snippet above costs you both files on every device. That is fine for a small thumbnail and unacceptable for a hero. When the bytes matter, write a real <picture> and point each <source> at the Next optimizer directly:

Art direction that only downloads one file
<picture>
  <source
    media="(max-width: 640px)"
    srcSet="/_next/image?url=%2Fhero-tall.png&w=480&q=75 480w,
            /_next/image?url=%2Fhero-tall.png&w=960&q=75 960w"
    sizes="100vw" />
  <Image src="/hero-wide.png" sizes="100vw" width={1600} height={500} alt="…" priority />
</picture>

The <source> wins on phones and the <Image> keeps optimising everywhere else — one file downloaded either way.

How to verify in the browser

Open DevTools, select the image, and read $0.currentSrc in the console — that is the file the browser actually chose. Compare the real pixel width of that file against $0.getBoundingClientRect().width * devicePixelRatio. If the file is far bigger, your sizes is lying. Do not use naturalWidth for this: with w descriptors it is density-corrected, so it reports the slot width back to you no matter which file was picked. Every readout on this page looks the real width up from the filename for exactly that reason.
